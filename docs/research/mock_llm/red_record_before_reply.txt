Mock LLM: a request is recorded before its reply goes out. Red run on the old ordering, then green (2026-10-08)

Seen: `py tests/run_tests.py --browser` failed mock_llm_match_filters_and_unmatched_fallback
(names == ["planner", "two-tools", None, "after-fail"] got the first three) under the browser suite's load; it
passed 3 of 3 alone and in the run without --browser. Cause: loom/agents/llm/mock_server.py `_Handler._dispatch`
called `st.record(rec)` only after `_send` / `_send_sse` had written the reply, so a client holding its reply could
read MockLLM.requests (or /mock/requests) before the server thread got back from the send.

New test: tests/suites/agents_mock_llm.py mock_llm_request_recorded_before_its_reply. It wraps this server's own
handler subclass so `_send` and `_send_sse` hold the handler 0.4 s after the reply is written (the window the loaded
machine gave the client), then reads MockLLM.requests right after a JSON reply, /mock/requests right after a second
one, and MockLLM.requests right after an event-stream reply; finally it waits for every `delivered` to be True.

## Fix
`_dispatch` records the rec (delivered None) before the delay and the send; `_State.mark_delivered` sets delivered
under the state lock once the send ends; `snapshot()` already copies under the same lock (a JSON round trip).
The L-272 disconnect test now waits for `delivered` to be set (not only for the record) and still asserts False.
