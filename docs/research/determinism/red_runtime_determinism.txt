2. Why the memo varied (the ticker race)
- gsap-core.js _attemptInitTween: a tween's first render is queued (lazy) when _lastRenderedFrame !== _ticker.frame;
  _lastRenderedFrame is set in Timeline.updateRoot on every ticker tick. Before the first rAF tick the two differ, so
  every first render made by the build waits in the queue; after one tick they match and each is written at once.
- Forced with GSAP's own API before Loom.boot: "ticked" = gsap.ticker.tick(); "unticked" = pause the global timeline,
  then tick (the frame counter moves, the root renders nothing). lab_places:
    ticked    rig parts right after boot: rotate(0.00 178 540), ... head rotate(...)   memo 317.67
    unticked  rig parts right after boot: no transform (their start pose still queued)   memo 318.06
  L-270's 6 of 10 at 318.06 were the unticked state: the build usually beat the first rAF.
- The race reached the build's own measurements: ava's walker getBBox at build was x 57.7, w 284.6 (start pose: arms
  out) or x 108, w 184 (no pose). With her feet at x 120 the figure check said "left side at x -22" (ticked) or nothing
  (unticked). The frames show the posed figure, so the unticked runs missed a real crop.

3. What the race did NOT do: frames under one seek order
- GSAP re-measures a fromTo's origin when the playhead first enters it (_initTween rebuilds the from-state tween), so
  the build-time memo was overwritten before any frame of the reveal: the pop fixture (ava pop, a second rig stamp),
  forced ticked and unticked, same seek order: identical hashes at 0.5, 1.1, 1.25, 1.45, 1.7, 3.0 s.

4. What did vary: the seek order (the real defect)
- The origin was measured at whatever time first entered the tween. Fixture tests/suites/runtime_determinism.py
  _REVEAL (ava pops at 1.0 s while raising her arm to wave; a card stamps at 1.0 s while its line settles 160 px up).
  Origins on the runtime before the fix (GSAP memo; matrix origin agrees in these orders):
    frame by frame from 0.5 s   ava (196.72, 460.35)   card (300, 255.91)
    jump straight to 1.1 s      ava (249.00, 459.87)   card (300, 228.83)
    3.0 s first, then back      ava (196.37, 443.58)   card (300, 195.00)
  Frame hashes at 1.1, 1.25 and 1.45 s differed between all three orders. Computed displacement at 1.1 s (origin
  difference x |1 - scale|): ava 52.3 px x 0.17 = about 9 px; card 60.9 px x 0.13 = about 8 px.
  Breathing alone (no wave) moved the origin about 0.4 px between orders and still changed the hashes.
- Where orders differ in production: HyperFrames renders in parallel workers and resumable segments (loom/render.py
  --workers, --resume), each worker's first seek lands at its segment start; the trailer seeks the lesson by its edit
  list (out of order); the frame review and the tests seek out of order.

6. The fix and which half closes which test
- boot.js: the master timeline has defaults { lazy: false } (trailer.js: its own timeline too).
- core.js: Loom.tween records the start of every tween with transformOrigin, svgOrigin, scale, rotation or skew;
  Loom.settleOrigins(tl) seeks to each start + 0.1 ms in time order, then to -1 s and 0 s. boot.js calls it after the
  clocks (element lives decide what is drawn) and before the shader layers (no GL draws in the pass).
- Half fixes (each a copy of the fixed runtime with one half removed):
    lazy: false only     seek-order test FAIL (same origins as before)   ticker test PASS
    origin pass only     seek-order test PASS, drawn about ava (180.00, 461.13): the queued start pose leaked into
                         the pass                                          ticker test FAIL
    both                 PASS, drawn about ava (180.99, 460.46), card (300, 274.94); the drawings' centres at 1.0 s
                         on a fresh page: (180.99, 460.46), (300, 275)
- GSAP's data-svg-origin is written only when GSAP measures; after a seek back it names the LAST tween measured on
  that element (after the fix: ava's memo at 1.1 s was her exit's origin while the frame used the pop's). The test
  reads the origin from the matrix: a scale s about (ox, oy) is matrix(s 0 0 s ox(1-s) oy(1-s)).
